## 0. 结论摘要

截图暴露的问题**不是"界面不好看"**，而是三类不同性质的东西：

| 类别 | 数量 | 代表 | 严重度 |
|---|---|---|---|
| **数据可信度** | 1 | 金额显示成 `22.990000000000002` | 🔴 **最高** —— 用户会以为数据坏了 |
| **死 UI / 缺失入口** | 2 | 对象页「刷新」按钮从未显示；无「新建表」 | 🔴 |
| **一致性 / 可读性** | 6 | 版本号 `v0.1.0 · P3`、耗时重复、端口 `0`、空行撑满 | 🟡 |

**一句话**：功能骨架是好的（六区、树、网格、查询页都在），
**但"数据看起来对不对"和"点得到点不到"这两件事上还有硬伤**。
`22.990000000000002` 这一条，比任何新功能都该先修。

与 Navicat 的差距结论在 §4：**不缺"能看"的能力，缺"能改结构"的能力** ——
建表 / 改表名 / 清空表 / 删表 / 加索引，**整块为零**。

## 2. 逐项问题（含代码证据与修法）

### 2.1 🔴 S1 — REAL/DOUBLE 列显示 IEEE754 长尾小数（最高优先）

**现象**（图 2）：`amount = 22.99` 显示成 `22.990000000000002`。

**根因**（单点）：

```java
// CellRenderer.java:216-221
private static String numberText(Object value) {
    if (value instanceof BigDecimal decimal) {
        return decimal.toPlainString();
    }
    return String.valueOf(value);   // ← Double 走这里，IEEE754 尾数直接暴露
}
```

- 演示库 `amount REAL`（`DemoDatabase:121`）→ SQLite `REAL` = 8 字节浮点 →
   JDBC 返回 `Double` → `String.valueOf(22.99d)` = `"22.990000000000002"`。
- **凡是 REAL / DOUBLE / FLOAT 列全中招**，SQLite 与 PG 都躲不掉。
- 数据页与查询页**共用**这一个渲染器（`QueryPage.ResultCell:1219` 调 `CellRenderer.render`），
  所以两页一起坏 —— 这也解释了两页现象一致。

**影响**：金额、评分、比率这类列会显示成"坏了的数据"。用户第一反应是"这工具不可信"。

**修法**（关键：**只改展示，不改值**）：

1. 展示层用 `BigDecimal.valueOf(double).stripTrailingZeros().toPlainString()`
   → `22.99`；再用列 `scale`（`ColumnDef` 已有 precision/scale）决定补零位数。
2. **编辑单元格时必须回填原始值**，不能把格式化后的字符串写回。
   `ValueCell` 的编辑器文本要独立于 `numberText`，否则会引入**新的数据损坏**。
3. 导出（CSV/TSV）走原始值，不走展示值 —— 否则导出精度被改。

**验收门禁**：`NumberFormattingTest`（🆕）
- `22.99d` → 展示 `22.99`，且编辑器回填与原值 `equals`
- `1e20`、`0.1+0.2`、`-0.0`、`null` 各一例
- 导出 CSV 的内容是原值字符串

### 2.2 🟡 M2 — 状态栏耗时重复

**证据**：`range` 字段自身带耗时（`DataGridPage:1330` 拼 `· 12 ms`），
而 `duration` 是**另一个独立字段**（`StatusBar:31`，`AppShell:1126` 单独 set）。
两者相邻显示，于是同一件事说两遍。

**修法**：二者取一。建议 **`range` 只说行范围，`duration` 独占耗时**，
这样查询页 / 数据页 / 结构页三处口径一致。

**验收门禁**：`StatusBarTest`（🆕）断言 `range` 文本不含 `ms`。

### 2.3 🟡 M1 — 版本号硬编码

**证据**：`StatusBar.java:35` → `segment("v0.1.0 · P3", ...)`，**无 setter**。
`AppShell.java:820` 关于对话框同一份字符串。现在已是第六轮，`P3` 严重过时。

**修法**：从构建产物取版本（`Implementation-Version`，Maven 已写进 jar manifest），
落一个 `AppVersion` 常量类，状态栏与关于对话框**共用**。
阶段代号（`P3`）应该删掉而不是手改 —— 它必然再次过时。

**验收门禁**：`StatusBarTest` 断言版本串来自 `AppVersion`，且**不含** `P` + 数字的阶段代号。

### 2.4 🟡 M3 / M4 — 连接列表的「不适用」与空行

**M3**：`ConnectionsPage:186-200` 四列直接绑原始值。
SQLite 的 `port()` 是 `0`、`host()`/`username()` 是空 → 显示 `0` 和空白。

**修法**：抽一个 `displayOr(—)`：空串 / null / **该方言不适用的 0** → `—`。
（注意只有 SQLite 才把 0 当"不适用"，MySQL/PG 的端口 0 是真的异常值，要能区分。）

**M4**：空行是 JavaFX 默认行为。建议在 `app.css` 给 `.table-row-cell:empty` 去边框 + 降底色，
让空行"消失"而不是"画出 12 个框"。

**验收门禁**：`ConnectionsPageTest.blankCellsUseDash`（🆕）+ 截图肉眼核对。

### 2.5 🟡 M6 / M7 / M8 — 数据页三处细节

| 项 | 修法 |
|---|---|
| **M6** 顶部「共 200 行」 vs 底部「1-200 / 500」 | 顶部改为「本页 200 行」，底部保持「1-200 / 共 500」。**用词必须区分"本页"与"全部"** |
| **M7** 「每页」下拉看不见值 | 给它 `minWidth`，或把底部条改成两行 |
| **M8** `id [PK] number · 自增` 挤一行 | 类型行只放类型；`PK` 徽标放列名字后；`自增` 用图标 + tooltip |

## 3. ⚠️ 我一开始看错、后来用代码推翻的三个判断

**这一段比问题清单更重要** —— 防止有人照着错的结论去改代码。

| 我的初判 | 代码事实 | 结论 |
|---|---|---|
| 「侧栏有**两个**搜索框」 | `SideBar` 里 `search` **只有一个**字段（:86），只放进底部 `bottomBar`（:381/:513）。顶部那个是 `manageConnections` 图标按钮（`Icons.CONNECT` **插头**）+ 连接下拉（:429） | ❌ **不存在重复搜索框**。真正的问题是**插头图标在 16px 下和放大镜高度相似**（见 L2），我和子代理都误读了 |
| 「记录导航条用 Unicode 符号 `\|◀ ◀ ▸ ▶\|`，违反 U-B4」 | `DataGridPage:875-885` 用的是 `Icons.Icon.FIRST / PREVIOUS / NEXT`，**是 SVGPath** | ❌ **不是 Unicode**。截图缩放到 1080px 后箭头像素化，看起来像文本 |
| 「`score` 显示 `7,5`，locale 小数点是逗号」 | `String.valueOf(7.5d)` = `"7.5"`；`numberText` 没有任何 locale 格式化 | ❌ **不是 locale 问题**。只有一个真实的数字问题，就是 **S1 长尾小数** |

这是与 Navicat 最大的一块差距，也是截图里最能感知到的（右键树 → 只有"打开数据 / 打开结构"）。

| **T2** | **清空表 TRUNCATE** | 🔴 零。`TRUNCATE` 只作为危险关键字存在（`DangerClassifier:76`） | 🟢 低 |
| **T3** | **重命名表** | 🔴 零。`RENAME TO` 只在 SQLite 重建内部用（:129） | 🟢 低 |

### 4.3 与 Navicat 的**结构性**差异（不是功能多少）

| 方面 | Navicat | 我们 |
|---|---|---|
| 对象操作入口 | 树右键 = 建表/设计表/截断/删除/转储 SQL | 树右键**只有 8 个只读动作** |
| 结构修改 | 可视化设计器（列/索引/外键/触发器/选项 五个页签全可写） | **只有列可写**，其余三页签纯展示 |
| 连接 | 连接属性页（SSL/SSH/高级） | 向导三步，无属性页 |
| 结果集 | 可分页、可编辑、可导出多格式 | 只读、上限 1000、CSV/TSV |

> 结论：**先把 T1–T4 做掉，界面"能改"这件事才算成立**。
> 这四项的 SQL 生成能力大部分已存在，预估是整个 backlog 里投产比最高的一组。

## 7. 门禁体系的缺口（本轮发现）

本轮 4 个缺陷（S1 / S2 / D1 / M1）**全部活在测试没有覆盖的路径上**，
443 条全绿。说明门禁只覆盖了"行为"，没覆盖"呈现"。

建议补三类门禁：

| 类型 | 断言什么 | 例 |
|---|---|---|
| **呈现门禁** | 控件被创建**且**在场景图里 | `lookup("#object-home-refresh") != null` |
| **格式化门禁** | 展示值与原值的双向一致性 | 展示 `22.99`、回填 `22.99d`、导出原值 |
| **文案门禁** | 状态栏字段不重复、版本无硬编码 | `range` 不含 `ms`；版本串来自单例 |

> 这类门禁成本很低（都是几行断言），但正好卡住本轮所有缺陷。
