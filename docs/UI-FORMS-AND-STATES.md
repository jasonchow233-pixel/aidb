# UI-FORMS-AND-STATES — 形态约定（弹窗 / 标签页）与状态约定（默认态 / 空白态）

> 本文回答三个问题：
> **① 一个新能力该做成弹窗还是标签页？** **② 启动时用户应该看到什么？**
> **③ 什么都没有的时候用户应该看到什么？**
>
> 起因：早期截图审计之后要补 T1–T4 等一批能力，
> 动手前必须先把形态定死 —— 「新建表做成标签页」这种错误一旦落地，
> 后面每个页面都要跟着改一遍。
>
> 对照：`docs/UI-GUIDE.md`（视觉规范） · `docs/UI-VISUAL-SPEC.md`（组件规格）。

---

## 0. 一句话结论

| 问题 | 结论 |
|---|---|
| **弹窗** | 一次性任务、需要阻断决策、改完就回原处 → **弹窗** |
| **标签页** | 会长期停留、需要并排比较、有状态要保留 → **标签页** |
| 最容易写错的 | **新建表 = 弹窗**（不是新标签）；**连接属性 = 弹窗里套 TabPane** |
| 默认态 | 已落地：常驻「对象」标签 + 演示库 |
| 空白态 | 9 处，已修 3 处（E1/E2/E3），本轮再修 2 处（E4/E6） |

## 1. 三种形态

先明确本项目里**实际存在**的三种容器（不是教科书分类）：

| 形态 | 代码特征 | 用户感受 |
|---|---|---|
| **模态弹窗** | `Dialog` / `Alert` + `initOwner(...)` + `showAndWait()` | 不处理完不能碰别的；Esc 关闭；有「取消」 |
| **多标签页** | `TabKind` 枚举 + `WorkspaceView` 里 `openTab(TabItem)` | 长期停留，可来回切换，有未保存状态 |
| **内联面板** | 塞进某个页面内部的 `TitledPane` / `VBox` | 不打断当前页面 |

> ⚠️ **第四种要警惕**：「弹窗里套 TabPane」。
> 连接属性（常规 / SSL / SSH / 高级）就是这种 —— 外层是**弹窗**（一次性配置），
> 内层是**多页签**（分区）。写成任何一边都不对。

## 2. 判定规则

按**顺序**判定，命中即停。写新能力时照这个走一遍。

### 2.1 做成「多标签页」的条件（命中任一）

| # | 条件 | 例 |
|---|---|---|
| T-a | 用户会**反复回来**、长期停留 | 表数据、SQL 查询 |
| T-b | 需要**并排比较** | 两个查询的结果、两张表 |
| T-c | 有**状态需要保留** | 未执行的 SQL、未提交的编辑 |

### 2.2 做成「模态弹窗」的条件（命中任一）

| # | 条件 | 例 |
|---|---|---|
| D-a | **一次性任务**，做完就结束 | 导入 / 导出向导、新建连接 |
| D-b | 需要**阻断**用户直到做出决策 | 删除确认、放弃修改 |
| D-c | 是对某个对象的**修改动作**，改完回到原处 | 编辑列、重命名列、改索引 |
| D-d | 结果**不需要保留** | 变量设置 |

### 2.3 判定顺序

```
① 它是"改一个已存在的东西"吗？       → 是：弹窗（D-c）
② 做完还要留在里面继续干活吗？        → 是：标签页（T-a/T-c）
③ 需要用户立刻做决定、否则不能继续吗？ → 是：弹窗（D-b/D-a）
④ 还是不确定？                       → 弹窗。弹窗比标签页容易退出，
                                        做错成弹窗的代价远小于做错成标签页
```

> 第 ④ 条是刻意的偏向：**标签页做错了会一直杵在那里，弹窗做错了关掉就行。**

## 5. 弹窗的实现规矩（三条硬性）

### 5.1 破坏性弹窗：默认按钮必须钉在「取消」

```java
DestructiveConfirm.of("删除表", "确定删除 orders？",
        "表和表里的数据都会被删除，且无法撤销。", "删除").confirmed()
```
它内部把破坏性按钮的 `ButtonData` 设成 `OTHER`（不是默认），
再在 `onShown` 里把「取消」设为 default。**回车 = 取消，不是删除。**

> 原因写在 `DestructiveConfirm` 的类注释里：早期版本用 `OK_DONE`，
> 于是「回车」直接删连接，是能在键盘上复现的数据丢失路径。
> T2/T3/T4 全部要走这个类，**不要自己 new Alert**。

### 5.2 弹窗必须跟随主题

```java
dialog.getDialogPane().getStylesheets().addAll(getScene().getStylesheets());
dialog.getDialogPane().getStyleClass().add("adb-dialog");
```
不写这两行的弹窗在深色主题下会是白的。现有 14 处都已处理，新的要照抄。

### 5.3 弹窗要有 owner

`dialog.initOwner(...)`。没有 owner 的弹窗会跑到屏幕中心、且可能被主窗口盖住。

## 7. 空白态（Empty State）

> 定义：**东西不存在 / 加载失败 / 搜不到时，用户看到的东西。**
> 目标：**每一处空白都必须告诉用户"为什么"和"下一步能干什么"**。

### 7.1 统一组件：`EmptyState`

```
图标（32px SVGPath，颜色交给 CSS）
标题    —— 说"这是什么状态"，不说"暂无数据"
说明    —— 说"为什么会这样 / 接下来能怎样"，460px 内换行
[按钮]  —— 动词短语（「新建连接」），不用「点击这里」
[提示]  —— 可选，放快捷键等补充信息
```

- 三参版 `of(icon, title, desc)`：**确实无处可去时**才用。
- 五参版 `of(icon, title, desc, actionText, action)`：**新空态一律用这个**。

## 10. T1–T4 落地记录（第八轮）

### 10.1 分层：谁负责什么

```
侧栏右键 / 数据库菜单 / ⌘K        ← 三条入口
        │
        ▼
SideBar.TableRequest(action, tableName, connectionId)
        │  侧栏只说清「点的是谁」，不知道怎么执行
        ▼
AppShell.runTableDdl(...)  →  TableDdl
        │  收输入 → 生成计划 → 展示 SQL → 确认 → 后台事务执行 → 刷新树
        ▼
StructureSqlBuilder + Dialect        ← SQL 由方言决定
        │
        ▼
StructurePlanRunner.execute(session, plan)   ← 单事务、失败回滚（与列级变更共用）
```

> ⚠️ **`StructurePlanRunner` 是刻意抽出来的**。
> 「先展示 SQL 再在单事务里执行」这套语义，结构页原本写在自己的私有方法里。
> 表级生命周期需要**完全相同**的语义 —— 抄一份就会变成两份会跑偏的实现：
> 将来改事务边界只改一处，另一处就成了静默丢数据的口子。现在两边共用同一个方法。

### 10.2 方言差异（这部分最容易被写死在 UI 里）

| 动作 | SQLite | PostgreSQL | MySQL |
|---|---|---|---|
| 重命名 | `ALTER TABLE "a" RENAME TO "b"` | 同左 | `RENAME TABLE \`a\` TO \`b\`` |
| 清空 | **`DELETE FROM "a"`**（没有 TRUNCATE） | `TRUNCATE TABLE "a"` | `TRUNCATE TABLE \`a\`` |
| 删除 | `DROP TABLE "a"` | `DROP TABLE "a"` | `DROP TABLE \`a\`` |
| 表注释 | ❌ 不支持（输入框禁用） | `COMMENT ON TABLE … IS '…'` | `ALTER TABLE … COMMENT = '…'` |
| 建表时主键位置 | 列定义末尾 | 列定义末尾 | **必须在 `COMMENT` 之前** |

> MySQL 那条是这次才发现的隐藏坑：`columnDefinition` 把 `COMMENT` 拼在最后，
> 直接追加 `PRIMARY KEY` 会得到 `` `id` INTEGER COMMENT 'x' PRIMARY KEY `` —— **语法错误**。
> 所以加了 `Dialect.createTableColumnDefinition(column, inlinePrimaryKey)`，
> 让方言自己决定主键插在哪（默认实现追加在末尾，MySQL 覆写插在 COMMENT 前）。

## 11. V1–V3 视图生命周期落地记录（R42 · N28-a）

### 11.1 为什么是弹窗，不是「视图对象页」

Navicat 的「新建视图 / 设计视图」是一个**设计器窗口**，不是一个常驻标签页。
我方当时的岔路口是「给视图做一张像查询页的对象页」还是「弹窗」—— 选弹窗的硬理由只有一条：
**视图没有数据页可停留**（表有 `GRID`，视图的数据只读），
建完视图之后没有内容需要长期挂着，按 §2.2 的 D-a 它就是「一次性任务 → 弹窗」。
另一个好处是复用已经落地的 T1 那条链：`ribbon.view` 和 `object.new-table` 行为一致，
于是原来挂在对象清单页上的「视图没有编辑器」如实说明页**可以删掉**，而不是留一个假落地页。

链路完全复用 §10.1：三条入口（功能区 `View` / 树右键 / 数据库菜单）→ `SideBar.TableRequest`
→ `AppShell.runTableDdl` → `TableDdl` → `StructureSqlBuilder` + `Dialect` → `StructurePlanRunner`。

### 11.2 方言差异：重建写法必须方言自报

| 动作 | SQLite | MySQL | MariaDB | PostgreSQL | Oracle | SQL Server |
|---|---|---|---|---|---|---|
| 新建 | `CREATE VIEW "v" AS SELECT …` | 反引号 | 反引号 | 双引号 | 双引号 | `[v]` |
| 重建 | **两句** 先删再建 | **两句** 先删再建 | 一句 `CREATE OR REPLACE` | 一句 `CREATE OR REPLACE` | 一句 `CREATE OR REPLACE` | 一句 `CREATE OR ALTER` |
| 删除 | `DROP VIEW "v"` | 反引号 | 反引号 | 双引号 | 双引号 | `[v]` |

写法由 `Dialect#viewReplace()` 返回 `ViewReplace` 枚举（`OR_REPLACE` / `OR_ALTER` / `DROP_THEN_CREATE`），
默认值是 **`DROP_THEN_CREATE`** —— 它是六种方言里唯一都认的写法，新方言忘了 override 也只会生成能跑的 SQL，
不会生成一句「看着对、执行必报错」的。
**MySQL 8.0 没有 `CREATE OR REPLACE VIEW`**（那是 MariaDB 的分支特性），这条最容易写错。

两句式带出一个真风险：**第一句 `DROP` 执行完，那个视图就已经没了**，
此刻依赖它的对象 / 另一个会话会立刻失败。所以计划里 `statements.size() > 1` 就
把 `approvalRequired` 置真 —— 预览显出两句，并额外弹一次确认。单句 `OR REPLACE` 不二次确认。

> ⚠️ 单句不等于「一定成功」：PostgreSQL 的 `CREATE OR REPLACE VIEW` **不允许改变列名/列数**，
> 改了会让服务端报错。我方不做「自动降级成先删再建」（那等于替用户决定要丢依赖），
> 而是让执行失败后经 `ErrorClassifier` 归类，把「发生了什么 + 建议怎么办」落到状态栏（V-12 同规）。

### 11.3 只收查询体，不收 DDL

界面让用户只写 `SELECT …`，`CREATE VIEW` 由方言拼。校验在模型层
（`StructureSqlBuilder#normalizeSelectBody`）：**预览与执行共用同一次归一化**，
所以「拦下来的形态」和「拼出来的语句」不会各判各的。拦四种：

| 输入 | 结果 |
|---|---|
| 空 / 只有空白 | `view.error.emptySelect` |
| 正文里带 `;`（两句） | `view.error.multiStatement` —— 否则一句 DDL 变两句，执行器按整批事务跑，用户以为只建了个视图 |
| 以 `CREATE` / `ALTER` / `DROP` 开头 | `view.error.fullDdl` —— 粘了整条 DDL，这里只收查询体 |
| 首词不是 `SELECT` / `WITH` / `VALUES` 也不是 `(` | `view.error.notSelect`（带上那个词，方便判断是不是粘错了） |

重名校验只在**新建**模式跑（重建模式「已经有这个视图」是前提，不是错误），
且对照的是 `existingTablesFor` —— **表名与视图名在同一命名空间**，只对照视图会让「和表撞名」拖到执行时才炸。

### 11.4 三处诚实条款的落点

1. **读不到定义就不开窗**：「设计视图」先在后台跑一次 DDL 读取，取回查询体再预填。
   读失败（权限 / 方言形状不认识）时**不开弹窗**、状态栏说明是哪个视图 ——
   用空 body 打开弹窗等于给用户一个「点确定就把真定义覆盖成空」的枪。
2. **名字格置灰而不是藏起来**：本版本没有视图重命名（六种方言写法各不相同），
   于是重建模式下名字输入框 `setDisable(true)` + tooltip 写明「请用新名字新建一个，再删掉旧的」。
   留一个能打字但不起作用输入框，就是 §5 说的骗人控件。
3. **视图节点不再挂表级动作**：原来表与视图共用一份右键菜单，视图上因此挂着
   「清空表 / 重命名 / 删除表」—— 点了只能失败的三项。现在按 `NodeKind` 分家，
   视图只给「设计视图 / 删除视图」；`sidebar.onlyTable.*` 那几条门禁文案继续守着键盘入口
   （树里选中视图后按快捷键仍会给「只有表可以清空」这类说明）。
